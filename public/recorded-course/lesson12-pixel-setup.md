# Пиксель и серверные события: пошаговая установка

**Дополнительный материал к уроку 12.** Актуально на 29 июля 2026.

Здесь всё, что не поместилось на слайды: куда нажимать, какой код вставлять, как проверить. Делай по порядку, не перепрыгивай.

---

## Часть 1. Пиксель в браузере

Это минимум. Без него реклама не оптимизируется вообще.

### Шаг 1. Создать датасет

В 2026 Meta называет пиксель **датасетом**. Это одно и то же: номер у него общий и для браузера, и для сервера.

1. Открой [Events Manager](https://business.facebook.com/events_manager2/)
2. Убедись, что вверху выбран нужный бизнес-аккаунт (частая ошибка - создать пиксель не в том кабинете)
3. Нажми **Connect data source** → выбери **Web** → **Connect**
4. Дай имя вида «Название продукта · Pixel»
5. Скопируй **Dataset ID** - 15-16 цифр. Он же Pixel ID.

Потом этот номер всегда лежит в разделе **Settings** твоего датасета.

### Шаг 2. Вставить базовый код

Базовый код сам отправляет событие «просмотр страницы» при каждой загрузке. Больше для этого ничего делать не нужно.

**Куда:** между тегами `<head>` и `</head>`, на всех страницах сайта.

Почему именно в `<head>`, а не внизу страницы: [так рекомендует сама Meta](https://developers.facebook.com/docs/meta-pixel/get-started) - ниже вероятность, что код заблокируют.

Выбери **один** способ из трёх. Не два сразу - иначе каждое действие посчитается дважды.

**Способ А. Вручную в код.** Подходит, если сайт свой или собран в Lovable.

Скопируй базовый код из Events Manager и отдай Claude с задачей:

```
Вставь этот код Meta Pixel между <head> и </head> так, чтобы он
был на всех страницах сайта. Покажи, какой файл ты изменил.

[СЮДА ВСТАВЬ БАЗОВЫЙ КОД ИЗ EVENTS MANAGER]
```

**Способ Б. Готовая интеграция.** Shopify, Wix, Squarespace, WooCommerce. В Events Manager выбираешь свою платформу и логинишься - дальше всё само. У Shopify в настройках канала Meta поставь уровень обмена данными **Maximum**: тогда включится ещё и серверная отправка, и часть второй половины этой инструкции тебе не понадобится.

**Способ В. Google Tag Manager.** Если доступа к коду страницы нет - Webflow, Framer, Tilda. Создаёшь тег Meta Pixel и триггер на нужные страницы.

### Шаг 3. Повесить событие

Базовый код считает только просмотры. Целевое действие надо отметить отдельной строкой - **на странице результата**, а не на странице, где человек что-то заполняет.

Покупка:

```html
<script>
  fbq('track', 'Purchase', { value: 49.90, currency: 'USD' });
</script>
```

Заявка:

```html
<script>
  fbq('track', 'Lead', { value: 50, currency: 'USD' });
</script>
```

Сумму передавай всегда. Без неё алгоритм ищет любую покупку, с ней - самые крупные. Для заявки ставь оценочную ценность: если из 10 заявок закрываешь одну на $500, пиши `value: 50`.

Полный список событий и их параметров - в [справочнике Meta](https://developers.facebook.com/docs/meta-pixel/reference).

**Главная ошибка новичков:** повесить `Lead` на страницу с формой вместо страницы после отправки. Тогда «заявкой» считается каждый, кто просто открыл форму, и алгоритм учится на мусоре.

### Шаг 4. Проверить

Не пропускай. Пять минут здесь экономят недели и деньги.

**Test Events** - главный инструмент:

1. Events Manager → твой датасет → вкладка **Test Events**
2. Вставь адрес сайта → **Open website**
3. Пройди путь покупателя до конца, как обычный человек
4. События должны появиться в панели за секунды

**Meta Pixel Helper** - расширение Chrome, [ставится отсюда](https://chromewebstore.google.com/detail/meta-pixel-helper/fdgfkebogiimcoedlicjlajpkdmockpc). С февраля 2026 требует логин в Facebook, иначе окно не откроется.

Важно понимать разницу: Pixel Helper показывает, что код **есть на странице**. Это не то же самое, что «данные дошли до Meta». Окончательная правда - только в Test Events.

**Event Match Quality** - оценка у каждого события в Events Manager, насколько хорошо Meta узнаёт человека. Цель - 6.0 и выше. Растёт, когда вместе с событием передаёшь email или телефон.

## Часть 2. Серверная отправка

### Зачем это вообще

У покупки два свидетеля.

**Браузер** - код на твоей странице. Ненадёжный: блокировщики рекламы и настройки iPhone затыкают ему рот. И есть дыра пострашнее - если человек оплатил и закрыл вкладку, не дождавшись возврата на твою страницу, события не будет вообще.

**Сервер** - сообщает о той же покупке напрямую. Заблокировать нельзя: это разговор двух серверов, в браузере пользователя блокировать нечего.

Проблема двух свидетелей: если оба доложат, Meta посчитает две покупки, и ты решишь, что реклама окупается вдвое лучше, чем на самом деле.

Решение - **номер чека**. Оба свидетеля называют один и тот же номер, Meta понимает, что это один случай, и склеивает.

### Что понадобится

1. ID датасета - уже есть из шага 1
2. Токен доступа - получишь ниже
3. Источник, который умеет сообщать об оплате
4. Место, где будет жить маленькая программа

### Шаг 1. Получить токен

Events Manager → твой датасет → **Settings** → раздел **Conversions API** → **Generate access token**.

Подробности - в [документации Meta](https://developers.facebook.com/docs/marketing-api/conversions-api/get-started). Приятная деталь: никакого ревью приложения проходить не надо.

**Этот токен - как ключ от квартиры.** Никогда не вставляй его прямо в код и не показывай на экране. Он живёт в «секретах» - защищённом хранилище, которое есть в любом сервисе для запуска кода.

### Шаг 2. Сделать эндпоинт

Эндпоинт - это адрес в интернете, который умеет принимать сообщения. Маленькая программа, которая ждёт сигнала от платёжки и пересылает его в Meta.

Где поселить, на выбор:

- [Supabase Edge Functions](https://supabase.com/docs/guides/functions/quickstart) - проще всего, если у тебя уже есть Supabase
- Railway или Vercel
- твой существующий бэкенд, если он есть

Код пишет Claude - универсальный промпт в конце этого документа.

### Шаг 3. Подключить источник

На примере Stripe ([документация](https://docs.stripe.com/webhooks)):

1. Открой [раздел Webhooks](https://dashboard.stripe.com/webhooks) в дашборде
2. **Create event destination**
3. Тип назначения - **Webhook endpoint**
4. Вставь адрес своей функции (обязательно `https://`)
5. В списке событий выбери **`checkout.session.completed`**
6. Скопируй **signing secret** (`whsec_...`) - он тоже идёт в секреты, по нему твоя программа проверяет, что запрос действительно от Stripe, а не от постороннего

Простыми словами: ты сказал платёжке «когда кто-то оплатит, стукни вот по этому адресу».

У других платёжек логика та же, отличаются названия разделов.

### Шаг 4. Настроить склейку

Чтобы Meta не посчитала покупку дважды, нужен общий номер чека.

**Со стороны сервера:** программа кладёт в поле `event_id` идентификатор платежа из платёжки.

**Со стороны браузера:** тот же номер надо передать четвёртым параметром. Для этого он должен попасть на страницу благодарности - в Stripe это делается через адрес возврата:

```
https://твойсайт.com/thank-you?session_id={CHECKOUT_SESSION_ID}
```

Фигурные скобки Stripe заменит на настоящий номер. Дальше код на странице читает его из адреса:

```html
<script>
  const id = new URLSearchParams(location.search).get('session_id');
  fbq('track', 'Purchase', { value: 49.90, currency: 'USD' }, { eventID: id });
</script>
```

Два условия, иначе склейка не сработает:

- номер совпадает символ в символ
- название события совпадает с учётом регистра: `Purchase`, а не `purchase`

### Шаг 5. Проверить

Сделай одну настоящую покупку на минимальную сумму и открой Test Events.

**Правильно:** одно событие Purchase, у которого указаны оба источника - браузер и сервер.

**Неправильно:** две отдельные покупки. Значит, номера не совпали. Чини сейчас, до запуска рекламы, иначе все цифры окупаемости будут завышены вдвое.

## Универсальный промпт

Заполни блок в начале и отдай Claude. Работает с любой платёжной системой и любым целевым действием.

```
Ты пишешь серверную отправку событий в Meta Conversions API.

════════ ЗАПОЛНИ ПЕРЕД ОТПРАВКОЙ ════════

[ВСТАВЬ: что я считаю успехом] — например: оплата подписки /
заявка на демо / регистрация аккаунта / старт диалога в боте

[ВСТАВЬ: откуда приходит сигнал] — например: Stripe / Paddle /
LemonSqueezy / Shopify / форма Tally / мой бэкенд на Supabase /
Telegram-бот. Напиши, умеет ли этот сервис слать вебхуки.

[ВСТАВЬ: где будет жить код] — Supabase Edge Functions /
Railway / Vercel / мой существующий бэкенд

[ВСТАВЬ: есть ли у события денежная ценность] — точная сумма
покупки / оценочная ценность заявки / ценности нет

[ВСТАВЬ: какие данные о человеке доступны] — email / телефон /
внутренний id пользователя / ничего

[ВСТАВЬ: адрес страницы, где происходит действие]

═════════════════════════════════════════

СНАЧАЛА, ДО КОДА:
1. Подбери подходящее стандартное событие Meta под то, что я
   назвал успехом, и объясни выбор одной строкой.
2. Проверь, реально ли получить сигнал из моего источника. Если
   он не умеет вебхуки — скажи прямо и предложи альтернативу,
   не выдумывай несуществующий вебхук.
3. Если чего-то не хватает или данные противоречат друг другу —
   задай мне вопросы и остановись. Не додумывай за меня.

ЗАТЕМ НАПИШИ КОД, который:
— принимает сигнал и проверяет его подлинность (подпись вебхука
  или секретный заголовок), чужие запросы отклоняет
— достаёт данные о событии
— отправляет событие в Meta Conversions API

В СОБЫТИИ ОБЯЗАТЕЛЬНО:
— event_name: выбранное стандартное событие, точный регистр
— event_time: время действия в секундах
— event_id: уникальный номер этого действия из моего источника
  (id платежа, id заявки, id пользователя) — нужен, чтобы Meta
  склеила серверное событие с браузерным
— action_source: подходящее значение
— event_source_url: адрес из блока выше
— user_data: все доступные данные о человеке, приведённые к
  нижнему регистру, без пробелов, захешированные sha256
— custom_data: value и currency, если ценность есть

Pixel ID и токен — только из переменных окружения META_PIXEL_ID
и META_CAPI_TOKEN. В код не вписывать.
Адрес запроса возьми актуальной версии API.
Логируй ответ Meta целиком, чтобы я видел ошибки.

В КОНЦЕ ОТДЕЛЬНО ВЫДАЙ:
— куда положить секреты в моём сервисе, по шагам
— как подключить вебхук в моём источнике, по шагам
— чек-лист: что я должен увидеть в Test Events
```

**Чего ждать от результата.** Промпт даёт рабочий каркас. Проверка подписи у каждой платёжки своя, и с первого раза Claude может ошибиться - это нормально, копируешь ошибку из логов обратно в чат и допиливаешь. Но саму проверку подписи выбрасывать нельзя: без неё кто угодно сможет слать тебе фальшивые покупки и портить обучение алгоритма.

## Шпаргалка: что чем считать

| Что продаёшь | Событие | Ценность | Номер чека берётся из |
|---|---|---|---|
| Оплата на сайте | `Purchase` | сумма платежа | id платежа |
| Заявка, демо, звонок | `Lead` | оценка стоимости лида | id заявки в форме или CRM |
| Бесплатная регистрация | `CompleteRegistration` | обычно нет | id пользователя в базе |
| Диалог в мессенджере | `Contact` | обычно нет | id чата |
| Начал оплату, не закончил | `InitiateCheckout` | сумма корзины | id сессии оплаты |
| Событий пока мало | `ViewContent` | нет | id страницы |

Правило проверки: выбранного события должно набираться около 50 в неделю. Не набирается - бери событие выше по воронке, а не увеличивай бюджет.

## Если сервера нет вообще

Бывает: конструктор без вебхуков и без доступа к коду. Тогда своего эндпоинта не будет, и это нормально. Варианты:

- готовый посредник **Stape** - от $10 в месяц, подключаешь пиксель, дальше он сам
- **Zapier** - для малых объёмов; дедупликацию не поддерживает, поэтому браузерное событие лучше отключить
- сменить инструмент на тот, где вебхуки есть

Не бейся неделю о невозможное.

## Частые ошибки

1. **Пиксель поставлен двумя способами сразу.** Каждое действие считается дважды. Выбери один.
2. **Событие висит на странице с формой,** а не на странице после отправки.
3. **Название события в другом регистре.** `purchase` и `Purchase` для Meta - разные события.
4. **Токен вписан прямо в код.** Уходит в репозиторий, оттуда куда угодно.
5. **Попытка дослать старые продажи.** События старше 7 дней Meta молча выбрасывает - ошибки не покажет, просто не примет.
6. **Адрес запроса скопирован из старого гайда.** У API меняются версии. Бери адрес из примера, который Meta показывает у тебя в Events Manager.

## Чего в 2026 делать уже НЕ нужно

Если встретишь в гайде совет «зайди в Aggregated Event Measurement и расставь приоритеты восьми событий» - гайд устарел. Meta убрала ручное ранжирование для сайтов в середине 2025 и агрегирует все события сама. Восьмёрка приоритетов осталась только для рекламы мобильных приложений на iOS.
